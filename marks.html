Marks, channels and graphs

A chart is a set of marks whose visual properties are driven by data. This lab builds the basic graphs from that idea, one decision at a time: which mark, which channel for which field, which scale, and when the obvious choice misleads.

This is the second page in a series. It assumes you have worked through A minimal D3 tutorial, so selections, joins, scales and axes are familiar. Nothing here is new D3 machinery for its own sake; the new material is about design, and the D3 is how you try the designs out. The next page, Color, does the same for the one channel that deserves a lab of its own.

How to use this page

Every grey code box is live. Edit it, press Run (or ⌘/Ctrl + Enter), and the output updates. Reset restores the original. Each example runs in isolation. Read the sections in order; expect about two and a half hours with the exercises.

1Data types

Before choosing a chart, classify the fields. The type of a field decides which operations make sense on it, and so which visual channels can represent it faithfully.

TypeWhat you can doIn the pitch data
Nominal (N)Tell values apart: =, ≠pitch_name, stand, description
Ordinal (O)Also order them: <, >inning, the count (balls-strikes)
Quantitative (Q)Also subtract, and often divide: differences and ratios mean somethingrelease_speed, release_spin_rate, launch_speed
Temporal (T)Quantitative with calendar structuregame_date, pitch order within a game
Spatial (S)Positions in a physical space; distance and direction matterplate_x, plate_z together: a location on a map of the strike zone

The type is a property of how you use the field, not of how it is stored. balls is stored as a number, but "2 balls" is not twice "1 ball" in any useful sense: treat it as ordinal. inning is ordinal too, though its equal spacing makes it safe to draw on a linear axis.

Here is a bar chart written the long way, as in the D3 tutorial. The x field is the count, which is ordinal, so the bars keep the count's own order instead of being sorted by height.

Sort the bars by height with counts.sort((a, b) => n.get(b) - n.get(a)). What do you gain, and what do you lose? For a nominal field like pitch_name, which order would you use?
Discussion

Sorted, the ranking is immediate: 0-0 comes first with 123 pitches, then 0-1 (71) and 1-2 (67), and 3-0 is last with 3. What you lose is the structure of the count. In the original order you can see that with zero or one strike, pitches thin out quickly as balls accumulate, while with two strikes 1-2 is the most common count. Keep an ordinal field in its order unless the only question is "which is biggest?"

A nominal field like pitch_name has no order of its own, so sort by value. The exception is a set of categories that appears in many charts, where one fixed order (like pitchTypes) lets readers find each category in the same place every time.

Example 1.2 again, with the helper. What is left is the part that is specific to this chart: the data, the scales' domains and the marks.

  
  
Watch out for one D3 shorthand. d3.scaleLinear([0, 10], [0, 500]) sets the domain and the range, but d3.scaleLinear([0, 10]) with a single argument sets the range, leaving the domain at its default of [0, 1]. The same goes for scaleBand and scalePoint. That is why the examples write d3.scaleLinear().domain([0, 10]) and let chart() fill in the range.

  
This is the same move as writing a plotting function around matplotlib's fig, ax = plt.subplots() and axis formatting. chart() returns the pieces you need to keep drawing, much as subplots returns ax.






  
3Marks and channels

  
Every chart decomposes into marks, the geometric primitives, and channels, the visual properties of the marks that you set from data.

  
    
    
  • Marks: points (dots, symbols), lines (paths, links), areas (bars, cells, regions).
    • 
    
  • Channels: position, length, angle, area, color lightness, saturation and hue, shape, and a few more (texture, orientation, motion).
    • 
  

  
Channels are not equal. Two principles decide which to use:

  
    
    
  • Expressiveness: the channel should express everything in the data and nothing more. Ordered data needs an ordered channel. Hue and shape have no natural order, so they suit nominal fields only.
    • 
    
  • Effectiveness: the most important field gets the channel people read most accurately. For quantities, experiments by Cleveland and McGill (1984) and many since give roughly this ranking: position on a common scale, position on unaligned scales, length, angle and slope, area, then color lightness and saturation.
    • 
  

  
You can feel the ranking. Below are the same five numbers, the pitch counts of each type, drawn six ways. The labels are letters so you have only the marks to go on.

  
  
In panels 1 and 2 you can read the order immediately and estimate ratios. With angles it is harder, with areas harder still, and lightness gives order but little sense of ratio. Hue gives neither: there is no reason green should be more than orange. That is the expressiveness failure: a rainbow on a quantity invites the reader to invent an order.

  
Write down your estimate of A ÷ E from each panel, then uncomment the console.log. Which channels were you closest with? Then replace d3.scaleSqrt in panel 4 with d3.scaleLinear and see how much larger the differences look.

  
Discussion
    
A is the 4-seam fastball with 187 pitches and E the curveball with 31, so A ÷ E is about 6. Estimates from position and length usually land close. Areas are usually underestimated, because perceived area grows more slowly than actual area, and lightness and hue give no usable ratio at all. With d3.scaleLinear in panel 4 the radius is proportional to the count, so the area ratio becomes 6² = 36: the fastball circle looks enormous.

  


  
Adding channels to one mark

  
A point mark can carry several fields at once: two through position, and more through hue, shape and size. Each extra channel is cheaper to add than to read. Below, the location of every pitch as it crossed the plate, with the strike zone drawn in, then with one channel added per panel.

  
  
Panel 2 works: pitch types pop out as regions because hue is read pre-attentively. Panel 3 does not: finding "sliders to left-handed batters" means scanning for a conjunction of hue and shape, which the eye does one mark at a time. Panel 4 had to drop most of the pitches to show size at all. A rule of thumb: position for the two fields that matter most, one more channel for a nominal grouping, and if you need a fourth field, reach for small multiples (section 7) or interaction.


  
Shape for pitch type

  
Shape is the other channel for nominal data. It survives grayscale printing and color vision deficiencies, but the eye reads it more slowly than hue, and only a handful of shapes are easy to tell apart. D3 has two sets of symbols: d3.symbolsFill, meant to be filled, and d3.symbolsStroke (circle, plus, times, triangle, asterisk, square, diamond), meant to be drawn as outlines, which stay distinguishable when they overlap. An ordinal scale maps each pitch type to one of them, just as pitchColor maps it to a color.

  
Below, the pitches from one game, so that the marks do not pile up. Start with shape alone and try to find every curveball. Then switch the menu to color, and to shape and color together.

  
  
With shape alone you have to look at the marks one by one: a plus and an asterisk, or a circle among crosses, do not pop out. With color the curveballs jump out at once, because hue is processed pre-attentively. Shape and color together is redundant encoding. It is no faster than color for most readers, but it keeps the chart readable in grayscale and for readers who cannot tell some of the colors apart. The Color page has a menu that shows each chart as a reader with a color vision deficiency sees it; come back to this example with that in mind.

  
Replace d3.symbolsStroke with d3.symbolsFill and set .attr("fill", ...) instead of the stroke. Which set is easier to read where marks overlap? Then show all five games instead of one: at what point does shape stop working?

  
One solution
    
    
Filled symbols merge into dark blobs where they overlap; outlines keep their shapes a little longer. With all five games neither works inside the strike zone, where the marks pile up: shape needs empty space around each mark to be read. Here it stops working somewhere between one game and two. Color, or small multiples by pitch type, go much further.

  


  
Expressiveness violations

  
The most common violation is a mark or channel that implies structure the data does not have. A line connecting nominal categories says "these are in sequence, look at the trend".

  
  
A line is appropriate for an ordinal x with equal steps. Change the left panel to mean speed by inning: group with d3.rollup(..., d => d.inning), use d3.range(1, 8) as the domain, and keep the line.

  
One solution
    
    
Now the slopes mean something: this is how the average changes from one inning to the next. But look at what the average is taken over. The rise to 94.7 mph in the seventh inning is not a faster arm: its 15 pitches were 47% fastballs and included no curveballs (example 6.2). An average over a mix of categories changes when the mix changes. A line can be expressive and still mislead.

  






  
4Bar charts and dot plots

  
Bar charts compare a quantity across categories: nominal or ordinal on one axis, quantitative length on the other. The questions to settle are how to order the bars, how to show a second categorical field, and whether the quantity should be a count or a share.


  
Grouped, stacked, normalized

  
Skubal throws to right-handed batters 404 times and left-handed batters 91 times in this sample. Suppose the question is: does he use a different pitch mix against lefties? Three ways to add the batter-side field:

  
  
The grouped chart answers "against which side does he throw more sliders?", which is not the question: he throws more of everything to righties. The stacked counts are dominated by the same imbalance. Only the normalized chart answers the question, and the answer is clear: lefties see far more sinkers (about a third of their pitches, against 8% for righties) and hardly any sliders. Choose the denominator before you choose the chart.

  
In the grouped chart batter side is shown with two greys rather than two of the pitch colors. The five pitch colors mean "pitch type" everywhere on this page and the next; reusing them for another field would make readers look for a connection that does not exist.


  
Dot plots when zero is not meaningful

  
A bar encodes a value by its length, so a bar chart must start at zero (section 9 shows what happens otherwise). When the interesting variation is far from zero, such as speeds between 78 and 100 mph, use a dot, which encodes by position alone, and zoom the axis. A dot also leaves room to show spread.

  
  
Add a second dot per row for pitches to left-handed batters, in a lighter tint of the same color, slightly below the first. Do his pitches get faster or slower against lefties?

  
One solution
    
    
Mostly the same. The 4-seam fastball (median 97.6 mph against lefties, 96.8 against righties) and the changeup (89.0 against 87.9) are about a mile per hour faster against lefties, but those lefty medians rest on 26 and 22 pitches, and the slider's on only 4. Printing n next to each interval is what keeps a reader from over-reading differences this small.

  






  
5Distributions

  
A mean or median hides the shape of the data. To show the shape of one quantitative field, bin it and count (a histogram), or draw every value (a strip plot), and summarize with quartiles (a box plot).


  
Histograms and bin width

  
d3.bin groups values into intervals; each bin is an array of the rows that fell in it, with x0 and x1 as its bounds. The bin width is a design decision with no single right answer. Drag the slider.

  
  
At 1 mph you can see three groups: curveballs around 80, changeups and sliders between 85 and 93, fastballs and sinkers between 94 and 100. At 5 mph the groups merge into a lump; at 0.25 mph noise looks like structure.


  
Every value, and a summary

  
To compare distributions across categories, put the category on one axis and draw each pitch as a dot, jittered vertically so the dots do not pile up. A box plot on top gives the quartiles. The jitter uses a seeded random generator so the picture is the same on every run.

  
  
Replace release_speed with release_spin_rate (change the x domain to [1600, 2800]). Which pitch type has the widest spread in spin? Then remove the box plots: with only 31 curveballs, do you still need them?

  
One solution
    
    
"Widest spread" depends on the measure. The changeup has the widest range, 1,619 to 2,082 rpm. The slider and the 4-seam fastball have the widest interquartile range, about 125 rpm each: their middle halves are the most spread out. That is why a box plot shows both the box and the whiskers.

    
Without the boxes, the 31 curveballs are all individually visible and a box adds little. The 187 fastballs overlap, and there the box summarizes what you can no longer count by eye.

  






  
6Lines and areas

  
A line connects measurements in order, so the reader looks at slope: rising, falling, flat. Use it when x is time or another ordered field with meaningful steps. The line itself is a claim that values between the points are sensible, so it needs enough points to be worth connecting.


  
Many lines, one in focus

  
Do starting pitchers lose velocity as the game goes on? Mean 4-seam fastball speed by inning, one grey line per game and the average of all five in color. Greying out the individual games keeps them as context without five competing colors.

  
  
Hover a grey line to see its game. The answer, for these five starts, is no: the average stays within half a mile per hour of 97 from the first inning to the sixth. The individual games bounce around more because each of their points averages only a handful of pitches. The seventh-inning bump is the least trustworthy point on the chart; check how many fastballs it averages over.

  
Print the number of fastballs per inning with d3.rollup(fastballs, g => g.length, d => d.inning). Then encode that count on the blue dots with a d3.scaleSqrt radius, so the reader can see which averages are weak.

  
One solution
    
    
The seventh-inning average rests on 7 fastballs, the third and fourth on 20 and 23, and the first, second and fifth on 36 to 38. The one point that looked like a change is the one with the least evidence behind it.

  


  
Stacked areas for composition over time

  
An area chart is a line chart with the space below filled; stacked, it shows parts of a whole changing over an ordered axis. d3.stack computes the layers and d3.area draws each as a band between its lower and upper edge.

  
  
Only the bottom layer and the total sit on a common baseline. The fastball share is easy to read; the slider band's thickness, floating in the middle, is not. Put the layer you most want read at the bottom.

  
Change the .keys(...) order so that sliders are the bottom layer. Then try d3.stack().offset(d3.stackOffsetWiggle), a streamgraph. What does it make easier to see, and what harder?

  
One solution
    
    
With sliders at the bottom their share can be read against the axis: 2% of pitches in the first inning, 15–21% in the second, third, sixth and seventh. The fastball, which used to be easy to read, now floats.

    
The streamgraph shifts the whole stack up and down to minimize how much the layers wiggle. The bands flow smoothly and the eye follows each one's shape, but no band sits on a baseline any more, so none can be measured, and the y axis has been removed because it no longer means anything. Streamgraphs suit many layers and a question about overall rhythm; they are a poor choice for reading shares.

  






  
7Scatterplots

  
A scatterplot shows the relationship between two quantitative fields: correlation, clusters, outliers. With 495 points, overplotting is the main problem, and the fixes are small marks, transparency and a thin light outline.

  
  
Each pitch type is its own cluster. Within each cluster, harder pitches tend to spin a little more (correlations between 0.2 and 0.4). A single correlation computed over all 495 pitches mixes that trend with the differences between types, and describes neither.


  
Small multiples

  
When colors overlap, split the chart: one panel per category, with the same scales everywhere and the other categories in light grey for context. Comparing panels is then comparing positions, which is the most accurate channel we have.

  

  
Size, and why area needs a square root

  
A symbol map places marks at locations and encodes a quantity in their size. Here the locations are on the strike zone rather than a map of the world, and the quantity is exit velocity for the 173 pitches that were hit. The perceived size of a circle is its area. If radius is proportional to the value, area grows with the square: a 114 mph ball looks twelve times bigger than a 32 mph one, when it is three and a half times faster. Most balls in play here were hit between 70 and 110 mph, so the two maps look alike at a glance; compare their legends to see how far apart the two encodings are.

  
  
Contact happens mostly in and just below the zone. Color the circles by pitch_name with pitchColor. With both size and color on overlapping circles, can you still answer "which pitch type got hit hardest"? Which chart from section 4 would answer it better?

  
One solution
    
    
No: with five colors and many sizes on overlapping circles, you cannot compare types. Put the type on an axis and the speed on position, as in section 5. The black ticks are medians. Among the types with many batted balls, the 4-seam fastball was hit slightly harder than the rest (median 80 mph, against 76 to 78). The curveball's higher median rests on only 4 batted balls, and the hardest single ball, 114 mph, came off a sinker.

  






  
8Matrices and heatmaps

  
A matrix puts one categorical field on each axis and encodes a quantity in each cell, usually with color. It trades accuracy for density: color is a weaker channel than position, but a matrix shows every combination at once and makes rows and columns easy to scan. Print the number in the cell when exact values matter.


  
Two categorical fields

  
What does Skubal throw in each count? Rows are pitch types, columns are counts, and each cell is the share of that count's pitches of that type, so every column sums to 100%.

  
  
Read along the rows. The changeup climbs to nearly half of his pitches with two strikes, while the sinker almost disappears. The curveball is never thrown in 1-0, 2-0, 3-0, 3-1 or 3-2, the counts where he most needs a strike. The columns with small n, such as 3-0 and 3-1, are where the colors are least trustworthy.


  
A heatmap over space

  
When both axes are quantitative positions, bin them into a grid and color each cell by its count. This is the same idea as a histogram, in two dimensions, and it is the standard way to look at where pitches go.

  
  
Binning loses the exact positions and depends on where the bin edges fall. A smooth alternative is a density estimate: d3.contourDensity places a small bump at every point, adds the bumps up and draws contour bands of the result. Below, one panel per pitch type. Each type's density is weighted to sum to one, so the colors compare where each pitch goes, not how often it is thrown.

  
  
Now the repertoire has a geography. The fastball lives in the upper half of the zone and the sinker in the middle. The slider sits low, and the changeup lower still, drifting to the catcher's right, away from right-handed batters. The curveball panel is lumpy because it rests on only 31 pitches: smoothing a small sample can draw confident-looking shapes that another five games would erase.

  
Change .bandwidth(14) to 5 and to 30. Like the bin width in section 5, the bandwidth is a smoothing choice that can create or hide patterns. Then restrict each panel to two-strike counts with d.strikes === 2.

  
One solution
    
    
At bandwidth 5 each panel breaks into islands around individual pitches; at 30 every type becomes one round hill. Neither is the truth, and 14 is a choice too.

    
With two strikes the fastball moves up (average height 3.20 ft, against 2.94 ft over all counts) and the changeup moves down (1.47 ft against 1.69 ft): he elevates one and buries the other when a swing and miss would end the at-bat. The panel titles show how few pitches some of these shapes rest on: 11 curveballs and 13 sinkers.

  






  
9Scales that tell the truth

  
Every chart so far had a scale whose domain someone chose. That choice can make a difference look huge or invisible without changing a single number.


  
Bars start at zero

  
The length of a bar is its value, so cutting off the bottom of the axis changes the ratios the reader sees.

  
  
On the left, the fastball bar is seven times as long as the curveball bar; the fastball is 20% faster. If the differences matter and zero makes them invisible, the answer is not to truncate the bars but to change the mark: the dot plot in example 4.2 zooms honestly, because a dot encodes by position, not length.


  
The domain sets the story on a line chart

  
Lines encode by position and slope, so they need not start at zero. The domain still matters: it decides how big a change looks. Here is the "all five games" line from example 6.1 with three y domains.

  
  
The first panel says nothing ever changes, the last says velocity swings wildly. Neither is a lie; both are uninformative about what matters. Choose the domain from the size of a difference that matters in the domain: for a pitcher, one mile per hour is a real change and a tenth is noise, so a range of about 90–100 mph is honest.


  
Shared scales for small multiples

  
Small multiples invite comparison across panels, which only works if the panels share scales. D3 will happily give each panel its own.

  
  
The y scales are still independent in both rows, because the question is about where speeds fall, not how many of each type there are. Decide per axis. When some values span orders of magnitude (populations, incomes, file sizes) use d3.scaleLog, and say so on the axis. A log scale has no zero, so it cannot be used for bars.
