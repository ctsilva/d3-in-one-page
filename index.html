A minimal D3 tutorial

Everything you need to go from a blank page to an interactive, linked visualization with D3: just enough HTML, CSS, JavaScript and SVG, then the small part of D3 that does most of the work.

D3 is not a charting library. It gives you a way to turn data into elements on a web page, and a toolbox of scales, shapes and behaviors for doing that well. Because it operates on the page directly, you cannot learn D3 without learning a little about how web pages are built. This tutorial covers that first, and keeps it minimal.

How to use this page

Every grey code box is live. Edit it, press Run (or ⌘/Ctrl + Enter), and the result below it updates. Reset restores the original. Examples run in isolation, so breaking one cannot break the others. Read in order the first time, because later sections assume the earlier ones. Expect about three hours, more if you do the exercises, which you should.

Yellow boxes like this one translate a concept into Python terms. Most of what you know about lists, dicts, comprehensions and pandas transfers; the surprising parts are the DOM and the way D3 binds data to elements rather than drawing a figure.

1HTML and the DOM

A web page is a text file written in HTML. It consists of elements, each written as an opening tag, some content, and a closing tag: <p>Hello</p> is a paragraph element. Elements nest, so a page is a tree. Tags can carry attributes, name-value pairs inside the opening tag, such as <a href="…">.

Try adding the two missing pitch types to the list, then a second paragraph. Notice that line breaks and indentation in the source do not matter; structure comes from tags alone.

The DOM

When the browser reads HTML it builds the tree in memory. That tree is the Document Object Model, or DOM. Everything that happens on a page after it loads, including everything D3 does, is a modification of that tree: adding an element, changing an attribute, removing a node. The HTML file is just the initial state.

Open your browser's developer tools (right-click, Inspect) on any page and look at the Elements panel. That is the live DOM, and you can edit it in place. Get in the habit of inspecting; it is how you debug D3.

Elements you will actually use

  • <div>: a generic block container. Most page layout is nested divs.
  • <span>: a generic inline container, for a few words inside a line.
  • <p>, <h1>…<h3>, <ul>/<li>, <a>: text, headings, lists, links.
  • <button>, <select>, <input>: controls.
  • <svg>: where the drawing happens. Section 4.
  • <script> and <style>: JavaScript and CSS, either inline or via src/href.

Two attributes matter more than the rest. id names one unique element; class tags any number of elements with a label. Both exist so that CSS and JavaScript can find elements.

This renders as plain text, because divs and spans have no appearance of their own. Structure and appearance are separate concerns; appearance is the job of CSS.

HTML is a tree, like a nested structure of dicts and lists, or an xml.etree.ElementTree. If you have used Jupyter, you have already been writing into the DOM: a notebook cell's output is a piece of HTML inserted into the page.

2CSS

CSS is a list of rules. Each rule has a selector, which says which elements it applies to, and a block of properties. The selectors you need:

These same selectors are what D3's select and selectAll take as arguments, so learning them pays twice.

Properties you will use constantly: color, background, font-family, font-size, width, height, margin (space outside an element), padding (space inside), border. And one you should know about: display: flex lays children out in a row.

Working with the data

pitches is an array of 495 objects. Filtering and mapping are plain JavaScript. For statistics and grouping, D3 has helpers that behave like pandas: d3.mean, d3.median, d3.extent (min and max as a pair), d3.rollup (group and aggregate).

d3.rollup(rows, reducer, key) is df.groupby(key).agg(reducer). It returns a Map, JavaScript's dict with non-string keys; iterate it with for (const [k, v] of map) or convert with Array.from(map). d3.group is the same without the reducer. There is no DataFrame: data is a list of row objects, and every column operation is a map.

Touching the DOM without D3

The browser's own API can create elements and set attributes. Knowing it exists demystifies D3, which is a thinner layer over this than it looks.

This is the pattern D3 automates: for each datum, create an element, set its attributes from the datum. Everything else in D3 is built on it.

4SVG

Divs can make bar charts, but not scatterplots or lines. For drawing, HTML has SVG, Scalable Vector Graphics: a set of elements for shapes that live in the DOM like everything else. That last part is what makes D3 possible. A circle is an element with attributes; a scatterplot is 495 circle elements; changing the data means changing attributes.

Coordinates start at the top-left corner, in pixels, with y increasing downward. This trips everyone up once.

The elements you need: rect, circle, line, text, path, and g. Shapes are colored with fill and stroke, which can be attributes as above or CSS properties. Position and size are always attributes, not CSS.

Groups and transforms

<g> is the div of SVG: an invisible container. Its purpose is the transform attribute. Moving a group moves everything inside it, which is how charts get their margins and axes get positioned.

Change the translate and watch the whole strike zone move. The circles keep their local coordinates. Hovering a circle changes its fill purely through CSS, no JavaScript.

A path takes a mini-language in its d attribute. You will rarely write it by hand; D3's shape generators (section 10) produce it for you. Recognizing M (move to) and L (line to) is enough.

Draw a scatterplot by hand

Here are the first five pitches, plate location in feet. To draw them we have to convert feet to pixels by hand: 40 pixels per foot, x measured from a center line at 150, and z flipped and measured from a baseline at 165 so that up is up. Feel how tedious this is.

Now imagine all 495, and then the request to make the plot twice as big. Every number changes. Computing pixel positions from data is what scales do in section 7, and generating one element per row is what data binding does in section 6. Together they replace this arithmetic entirely.

SVG is the closest thing to matplotlib's artist layer: a circle element is a Circle patch, a g is roughly an Axes with its own transform. The difference is that in SVG every artist stays addressable after drawing, and CSS and mouse events can reach it.

5D3 selections

D3 is loaded on a page with one script tag, before your own code:

<script src="https://cdn.jsdelivr.net/npm/d3@7"></script>
<script>
  // d3 is now a global object
</script>

Everything starts with a selection. d3.select("body") finds the first element matching a CSS selector and wraps it in an object with methods for changing it. append adds a child element and returns a selection of the new element, so calls chain.

The methods you will use, in order of frequency:

  • attr(name, value): set an attribute. The workhorse.
  • append(tag): add a child; returns the child.
  • text(value): set the text content.
  • style(name, value): set an inline CSS property.
  • classed(name, true/false): add or remove a class, so CSS can do the styling.
  • select(selector) / selectAll(selector): find one or all descendants.
  • remove(): delete the elements.
  • on(event, handler): listen for mouse or keyboard events. Section 9.
  • call(fn): pass the selection to a function; used for axes and brushes.

Almost every method returns the selection it was called on, which is why D3 code reads as long chains. The exception is append, which returns the new child. Read chains top to bottom: each line modifies what the previous line produced.

Chaining works like method chains on a DataFrame: df.query(…).groupby(…).mean(). Each call returns an object to call the next method on. The append exception is like a method that returns a different object; after svg.append("g") you are holding the g, not the svg. Keep the parent in a variable when you need it later, as with svg above.

Selecting many elements

selectAll returns all matches. A method called on it applies to every element. Instead of a constant, you can pass a function, and D3 calls it once per element with the element's datum and index. Datum comes in section 6; for now the index alone is useful.

The loop in that example is a smell. Creating elements one per data item, then setting their attributes from the data, is exactly what D3's data binding does, without the loop.

6Binding data

The central idea of D3, and the one that is genuinely new if you come from matplotlib: you do not draw the data. You bind an array to a selection, and D3 creates, updates or removes elements so that there is one element per array item. Each element remembers its datum, and from then on, attribute functions receive it as d.

The pattern is three calls:

svg.selectAll("circle")   // 1. the elements you want to exist (possibly none yet)
   .data(array)           // 2. the data they should correspond to
   .join("circle")        // 3. create/remove elements until they match

The result is a selection of one circle per datum, ready for attr. Here is the pitch-mix bar chart from section 2, generated rather than typed.

Change a count, add a sixth entry, or sort mix before binding it. Note also that rows.append("span") appends to each of the five rows, and the appended children inherit the datum, which is why d => d.name works on the span.

In matplotlib you call ax.bar(names, counts) and get a picture. In D3 you say "there should be one div per row of mix" and then describe each div's attributes as functions of its row. It is declarative about what exists and functional about how it looks. The upside comes when the data changes: rebinding new data updates existing elements in place, which is what makes smooth interaction possible.

Loading data from a file

Real data comes from a file. d3.csv(url) fetches and parses a CSV and returns a promise, because fetching takes time; you attach the code that needs the data with .then. Every value comes back as a string, so pass d3.autoType to convert numbers and dates.

Notice the order of the printed lines. All of your drawing code goes inside the .then callback, or in an async function with const rows = await d3.csv(…), which reads more naturally.

Browsers refuse to fetch local files from a page opened via file://. Serve your project directory instead: python -m http.server, then open http://localhost:8000. On this page, the example above falls back to an embedded copy of the CSV when it is opened as a file, so it works either way. In your own projects, the variable pitches will not exist; you load your data.
d3.csv(url, d3.autoType) is pd.read_csv, returning a list of dicts rather than a DataFrame. Promises are the equivalent of awaiting an aiohttp request. There is no blocking read in the browser.

Join handles change

Call the same selectAll…data…join again with different data, and D3 reuses existing elements, creates the extra ones needed, and removes the surplus. Put the drawing in a function and call it whenever the data changes.

Pick a different game. The circle count follows the data. Older D3 code spells this out as enter(), exit() and an update selection; join does all three, and you can pass it functions to customize each phase when you need to.

7Scales and axes

A scale is a function from data values to pixel values. You give it a domain (the range of the data) and a range (the pixels available), and it does the arithmetic that section 4 did by hand.

Three scale types cover nearly everything:

  • scaleLinear: number to number. Positions, sizes, opacity.
  • scaleBand: category to a slot of equal width, for bar charts. x.bandwidth() is the bar width.
  • scaleOrdinal: category to anything, typically a color. Pass a fixed list of categories so colors never depend on data order.

Others exist (scaleTime, scaleLog, scaleSqrt, sequential color scales); they have the same shape.

The margin convention

Axes need room outside the plotting area. The universal D3 pattern is to declare a margin object, size the SVG to include it, and set each scale's range to the inner area. An axis is then a component you call on a group placed at the right edge; it reads the scale and draws ticks and labels.

Compare this to example 6.2: the only change is that 150 + d.plate_x * 40 became x(d.plate_x). Resize the SVG or change the domain and nothing else needs to change. Add a rect for the strike zone: it spans x(-0.83) to x(0.83) horizontally and, for a typical batter, y(3.2) to y(1.6) vertically. Remember that the rect's y is its top edge.

Band and ordinal scales

Two details worth noticing. The bar's height is a difference of two scaled values, because y runs downward. And d3.format(".1f") creates a formatting function, using the same mini-language as Python's format specs.

A scale is np.interp with a memory: x = scaleLinear().domain([a, b]).range([c, d]), then x(v). Matplotlib does this invisibly inside an Axes; D3 makes it an explicit object so that you can reuse it for positions, axes, brushes and inverse lookups. d3.format(".1f") is "{:.1f}".format, partially applied.

8Two charts

Everything above now assembles into the two charts that appear in nearly every visualization: a bar chart and a scatterplot. Each is written as a function that takes data and returns an SVG, which is how you will want to organize real code.

Bar chart: pitch mix

Horizontal bars, sorted, with the counts computed from the raw rows rather than typed in. Bars are sorted because the order carries no information, so we use it to make comparison easy.

d3.create("svg") makes a detached element, so the function returns a node and the caller decides where it goes. Try barChart(pitches.filter(d => d.stand === "L")) to see the mix against left-handed batters.

Change the chart to show mean release_speed per pitch type rather than count. Then show the share of each type as a percentage using d3.format(".0%").

Scatterplot: movement by pitch type

Horizontal versus vertical movement, in inches, colored by type. This is the plot that shows what a pitcher's repertoire is: each type occupies its own region. Color needs a legend, and the legend is just another data join.

Two habits to keep from this example. The color scale is defined outside the chart function with a fixed category order, so the same type gets the same color in every chart on the page, regardless of which types happen to be present. And the axis labels say what the units are.

Five colors is the practical limit for identifying categories by hue, and even five cannot be told apart by every reader. When there are more categories, or when the identity really matters, use small multiples: one panel per category, with the others in grey for context. A good exercise after this section is to draw five copies of this scatter, one per pitch type, with the other four types in grey.
Make a second scatter of release_speed against release_spin_rate by passing the accessor functions as parameters, so one function draws both. Then map launch_speed to radius for the pitches that were hit, using d3.scaleSqrt so area, not radius, is proportional.

9Interaction

Because every mark is a DOM element, interaction is just event handling. selection.on(event, handler) registers a listener on each element; the handler receives the browser event and the datum. The events you need are mouseenter, mouseleave, mousemove and click.

Hover and tooltips

A tooltip is an absolutely positioned div that follows the mouse. d3.pointer(event) gives coordinates relative to the element, which is convenient for placing it.

event.currentTarget is the element the handler is attached to; wrapping it in d3.select lets you modify just that one. For dense plots, hovering a 3-pixel circle is fiddly; the fix is to find the nearest point with d3.quadtree or a Delaunay triangulation (d3.Delaunay), which the D3 docs cover.

Brushing and linked views

The interaction that defines InfoVis: select in one view, see the selection in another. d3.brush is a behavior you call on a group; it draws the drag rectangle and fires events with the selection in pixel coordinates. You invert those through the scales, or compare them to scaled positions, then update the other views.

The structure is the thing to learn, more than any line. There is one piece of state, the selected set. One function, update, renders that state into every view. The brush handler computes the state and calls update. A filter dropdown, a legend click or a search box would all do the same. That is how a real explorer combines several brushes, a game filter and pitch-type toggles without the views ever disagreeing.

Note that the brush gives pixel coordinates and we compare scaled positions to them. The alternative is to invert: release.x.invert(x0) gives feet, which is what you want if the selection should survive a resize.

Add a brush to the movement panel too, so that a pitch must be inside both rectangles. Then make the legend in example 8.2 clickable to toggle a pitch type on and off. Both are changes to how the selected set is computed; update stays the same.

Lines and shape generators

d3.line() turns an array of points into the d attribute of a path. Configure it with accessor functions, then call it on the data. Here, velocity pitch by pitch through one game, one line per pitch type.

Note that data(byType) binds a Map: each datum is a [key, rows] pair, destructured in the accessors. d3.area, d3.arc and the curve interpolators (.curve(d3.curveMonotoneX)) work the same way.

Transitions

Insert .transition().duration(ms) into a chain and the attribute changes that follow are animated instead of instant. Use it to show that an element changed, not for decoration.

Reading further

  • d3js.org: the official documentation, organized by module, with an example for everything. Read Selections, Joining data and Scales first.
  • The D3 gallery on Observable: hundreds of complete, forkable examples. Observable notebooks run cells in a slightly different environment; the D3 code is the same.
  • MDN on SVG and on JavaScript: the reference for everything that is not D3.
  • Scott Murray, Interactive Data Visualization for the Web, 2nd edition (O'Reilly, 2017), and his earlier online D3 tutorials: the classic long-form introduction, and the inspiration for this page. Their code uses D3 v3 and v4, so translate enter().append() to join().
If you want charts quickly and reproducibly from Python, use Altair: it emits Vega-Lite, a grammar of graphics that runs in the browser, and it covers a large fraction of what people build in D3 with far less code. Reach for D3 when the visualization is novel, when interaction needs to be custom, or when the figure is part of a larger interactive page. Knowing D3 also makes Vega-Lite's model easy to read, since both rest on the same scales, marks and encodings.
